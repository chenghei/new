# 并发处理与安全设计

本文说明系统在多用户并发访问下的数据一致性方案、安全防护措施，以及实测验证结果。所有结论均来自代码实现与真实并发请求验证。

---

## 一、并发问题与解决方案

电商系统最典型的并发风险是「超卖」「重复扣减/回补」「重复提交」。本项目针对性地处理了以下场景：

| 场景 | 原来的问题 | 现在的方案 | 代码位置 |
|---|---|---|---|
| 单商品下单扣库存 | 先读库存→判断→写回绝对值，属于读改写竞态，并发会超卖 | 事务 + **原子 SQL**，用 `WHERE stock >= qty` 与 `affectedRows` 判定 | `orderController.createOrder` |
| 购物车批量结算 | 事务外校验、事务内按旧值写回，仍有超卖；且无行锁 | 事务内**逐件原子扣减**，任一失败整体回滚 | `orderController.batchCreateOrders` |
| 模拟支付 | 先查状态再更新，可能重复支付 | **条件更新** `WHERE status='pending'` | `orderController.payOrder` |
| 确认收货 | 同上，可能重复确认 | 条件更新 `WHERE status='shipped'` | `orderController.confirmOrder` |
| 取消订单 | 并发取消会**重复回补库存**（回补两次） | 条件更新 `WHERE status='pending'`，只有成功流转的那一次才回补 | `orderController.cancelOrder` |
| 售后完成回补库存 | 重复处理会重复加库存 | 订单**条件流转**（非已取消→已取消）成功才回补 | `afterSaleController.processAfterSale` |
| 售后重复申请 | 先查后插，并发可产生两条进行中的申请 | 事务 + **行锁**（`lock: LOCK.UPDATE`）串行化 | `afterSaleController.applyAfterSale` |
| 收藏并发切换 | 并发插入触发唯一索引 → 返回 500 | 捕获唯一约束冲突，按「已收藏」友好返回 | `favoriteController.toggleFavorite` |

### 1. 库存：原子扣减（最核心）

```sql
UPDATE products
SET stock = stock - ?, sales = sales + ?, updated_at = NOW()
WHERE id = ? AND status = 'active' AND stock >= ?
```

- 「判断库存是否充足」与「扣减」在**同一条 SQL 内原子完成**，由数据库保证不会出现两个请求都读到 `stock = 1` 而都扣成功的情况。
- 通过返回的 `affectedRows` 判断结果：`0` 表示库存不足/已下架/不存在，直接抛业务错误并回滚。

### 2. 订单状态流转：条件更新（幂等）

```sql
UPDATE orders SET status = 'cancelled'
WHERE id = ? AND user_id = ? AND status = 'pending'
```

- 只有 `affectedRows === 1` 的请求才算成功；重复/并发请求自然失效。
- 取消订单与售后完成的**库存回补都挂在这个条件更新成功之后**，因此库存最多回补一次。

### 3. 售后申请：事务 + 行锁

```js
await sequelize.transaction(async (t) => {
  const order = await Order.findOne({ ..., transaction: t, lock: t.LOCK.UPDATE });
  // 校验订单状态、类型
  const existing = await AfterSale.findOne({ ..., transaction: t, lock: t.LOCK.UPDATE });
  if (existing) throw bizError(400, '该订单已有进行中的售后申请');
  return AfterSale.create({ ... }, { transaction: t });
});
```

- 并发请求会在同一订单行上排队，后到者能看到先到者已创建的申请，从而被拒绝。

## 二、并发验证结果（真实请求）

> 测试方式：通过 HTTP 并发发起真实请求，直接读写数据库核对库存、销量与记录数；测试后清理临时数据。

### ① 超卖测试：库存 5，同时发 10 个下单请求
```
CONCURRENT_CREATE total=10 success=5 statuses=[201,201,201,400,201,201,400,400,400,400]
AFTER_CREATE stock=0 sales=5
```
→ 恰好 5 单成功、5 单被拒（库存不足），**库存归零、未超卖**。

### ② 重复取消测试：对同一待支付订单同时发 3 个取消请求
```
CONCURRENT_CANCEL success=1 statuses=[200,400,400]
AFTER_CANCEL stock=1 sales=4
```
→ 只有 1 次成功，**库存只回补 1 次**（0→1），销量只减 1。

### ③ 正常流程回归（确认没有改坏主流程）
```
create 201 → pay 200 → pay AGAIN 400 → ship 200 → confirm 200 → confirm AGAIN 400 → cancel(已完成) 400
final stock=8 sales=2  (期望 8 / 2)
```
→ 正常链路全通，重复操作被正确拒绝，库存与销量一致。

### ④ 售后重复申请：同一订单同时发 3 个申请
```
CONCURRENT_AFTER_SALE statuses=[201,400,400]
messages=["售后申请已提交，请等待处理","该订单已有进行中的售后申请","该订单已有进行中的售后申请"]
after_sale rows=1   order status still=paid
```
→ 只创建 1 条申请，其余被拒绝；订单状态未被误改。

### ⑤ 收藏并发：同时发 5 个收藏切换请求
```
CONCURRENT_FAVORITE statuses=[201,201,201,201,201] has500=false
favorite rows=1
```
→ 全部正常返回、无 500，最终只产生 1 条收藏记录。

## 三、安全设计

| 维度 | 措施 | 位置 |
|---|---|---|
| 密码存储 | bcryptjs 哈希，cost = 10；创建/修改密码时自动加盐哈希，查询接口一律排除 `password` 字段 | `models/User.js` hooks、`toSafeJSON()` |
| 身份认证 | JWT（HS256，默认 7 天过期），请求头 `Authorization: Bearer <token>` | `utils/jwt.js`、`middleware/auth.js` |
| 接口鉴权 | `authenticateToken`（必须登录）、`optionalAuth`（可选登录）、`requireRole/requireAdmin`（角色校验）；管理端 `/api/admin/*` 在路由层统一挂载管理员校验 | `middleware/auth.js`、`routes/*` |
| 越权防护 | 订单/商品/售后/地址等均按 `user_id` 归属过滤；商家只能操作自己商品的订单与售后；非管理员仅能看到上架且审核通过的商品 | 各 controller |
| 安全响应头 | Helmet，并放开 `crossOriginResourcePolicy` 以便三端加载 `/uploads` 图片 | `app.js` |
| 跨域控制 | CORS 白名单仅放行 `localhost:3000~3003`（可由环境变量覆盖） | `app.js` |
| 限流 | `express-rate-limit` 作用于 `/api`：开发 3000 次/15 分钟，生产 1000 次/15 分钟 | `app.js` |
| 上传安全 | Multer 限制仅 jpg/png/gif、单文件 ≤ 5MB，文件名随机生成（时间戳+随机数），统一落到 `backend/uploads` | `utils/upload.js` |
| 密钥保护 | 管理员端读取 AI 配置时仅返回脱敏密钥（`sk-4****c28d`）与来源，不回传明文 | `aiAdminController.getConfig` |
| 注入防护 | 通过 Sequelize ORM 与参数化 `replacements` 访问数据库，不拼接用户输入 | 全部 controller |
| 参数校验 | 注册/登录/改密使用 Joi 校验；手机号、身份证号、金额、库存等在控制器层二次校验 | `utils/validation.js`、各 controller |
| 连接池 | Sequelize 连接池 `max: 10`，避免连接数失控 | `config/database.js` |

### AI 服务配置的读取优先级
1. 数据库 `ai_configs`（管理员端可在线维护，密钥留空表示不修改）
2. 回退 `.env` 的 `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` / `DEEPSEEK_MODEL`

管理员可随时停用 AI 服务（`enabled = false`），停用后所有 AI 能力返回明确错误而不影响主流程。

## 四、实施过程中修复的两个隐患（踩坑记录）

### 1. `sequelize.sync({ alter: true })` 导致索引膨胀、启动失败
- **现象**：后端启动报 `Too many keys specified; max 64 keys allowed`，服务无法启动。
- **原因**：`alter: true` 每次启动都会重建唯一索引，多次重启后 `users` 表索引累积到 64 个（MySQL 单表上限），`categories`、`orders` 也各有 32 个冗余索引。
- **处理**：清理 119 个自动生成的多余索引；并把 `app.js` 改为**默认不 alter**（`sequelize.sync()`），需要同步表结构时临时设置环境变量 `DB_SYNC_ALTER=true` 启动一次。

### 2. 上传目录与静态目录不一致，导致上传后图片 404
- **现象**：图片能上传成功，但页面上访问 `/uploads/xxx.png` 返回 404。
- **原因**：Multer 存到仓库根目录的 `image/`，而 Express 只对外暴露 `backend/uploads/`。
- **处理**：统一为 `backend/uploads`（绝对路径），迁移历史文件并删除多余目录；静态目录也用绝对路径挂载，避免受启动目录影响。

## 五、Redis 应用（本次新增）

针对 AI 调用成本/并发与 JWT 登出失效三个问题引入 Redis，均支持**优雅降级**（`REDIS_ENABLED` 非 true 或连接异常时自动回退，不影响任何主流程）。

| 用途 | 方案 | 位置 |
|---|---|---|
| AI 结果缓存 | 按用户缓存推荐结果，TTL 默认 600s，命中直接返回，减少 DeepSeek 调用 | `config/redis.js`、`aiController.getRecommendations` |
| AI 并发控制 | Redis 计数器限制全局同时在跑的 AI 请求数（默认 5），超出返回 429；推荐接口自动降级热销 | `config/redis.js#acquireSlot`、`aiController.callDeepSeek` |
| JWT 登出黑名单 | 登出时将 token 写入黑名单（TTL = token 剩余有效期），鉴权中间件校验，解决 JWT 无状态、登出后 token 仍有效的问题 | `authController.logout`、`middleware/auth.js` |
| 分布式锁 | 多实例部署下串行化跨实例的「检查-写入」：下单按商品、结算按用户、售后按订单；`SET key token PX ttl NX` 加锁 + Lua 比对 token 解锁，避免误删他人锁 | `utils/redisLock.js`、`orderController`、`afterSaleController` |

### Redis 持久化

为避免 Redis 重启后 **JWT 登出黑名单丢失**（导致已登出的 token 复活），Redis 已开启 **AOF 持久化**（`appendonly yes` + `appendfsync everysec`），并保留 RDB 快照作为兜底；同时设置 `maxmemory-policy noeviction`，防止黑名单等关键 key 被内存淘汰。配置文件：`.redis/redis.conf`。

- 实效：AOF 每秒落盘，**崩溃场景最多丢 1 秒数据**；重启后 key 与 TTL 完整恢复。
- 实测：写入模拟黑名单 key（`EX 300`）后重启 Redis，`exists` 仍为 1、`ttl` 正确递减。

### Redis 启动与验证

本项目使用免安装绿色版 Redis（Windows），解压在项目根目录 `.redis/`（已加入 `.gitignore`，不入库）。**启动时必须带上配置文件**，否则 AOF 持久化不生效、重启后黑名单会丢失。

```powershell
# 启动（必须带 redis.conf，否则持久化失效）
& 'd:\biyesheji\.redis\redis-server.exe' 'd:\biyesheji\.redis\redis.conf'
```

```powershell
# 验证服务是否开启：返回 PONG 即正常
& 'd:\biyesheji\.redis\redis-cli.exe' ping

# 验证持久化是否开启：应返回 yes / everysec
& 'd:\biyesheji\.redis\redis-cli.exe' config get appendonly
& 'd:\biyesheji\.redis\redis-cli.exe' config get appendfsync

# 查看运行中的 key（可看到缓存、锁、登出黑名单）
& 'd:\biyesheji\.redis\redis-cli.exe' keys *

# 停止 Redis
& 'd:\biyesheji\.redis\redis-cli.exe' shutdown
```

> 还需在 `backend/.env` 中设置 `REDIS_ENABLED=true` 才会启用 Redis 相关能力；若 Redis 未启动或该值为 false，系统自动降级，不影响主流程。

## 六、已知限制与后续可改进方向

1. **分布式部署**：并发控制以数据库原子操作/事务行锁为第一道防线（单库不超卖），并引入 Redis 分布式锁作为多实例部署下的第二道防线，串行化跨实例的「检查-写入」操作（下单扣库存、购物车结算、售后申请）；Redis 未启用时锁自动降级，主流程不受影响。
2. **敏感数据加密**：身份证号、AI 密钥在库中为明文（接口层已脱敏），生产环境建议字段级加密 / KMS 托管。
3. **图片处理**：未做压缩、水印、内容安全检测，也未接入对象存储；高并发上传建议改为直传 OSS + CDN。
4. **AI 调用治理**：已增加结果缓存与全局并发上限；后续可补充失败重试与按用户维度的细粒度限流。
5. **自动化测试**：`jest`、`supertest` 已安装但尚未编写测试用例，建议补充关键路径（下单、支付、库存、鉴权）的单元与集成测试。
6. **限流粒度**：目前为全局限流，可针对登录、下单、AI 等敏感接口做更细粒度的独立限流。
